# Development

## Environment variables

All configuration comes from environment variables (or `.env`, which is git-ignored).
See `.env.example` for the full list.

| Variable | Default | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | local Docker Postgres on `127.0.0.1:5432` | SQLAlchemy URL; use the `postgresql+psycopg://` prefix |
| `DATABASE_SSL_MODE` | unset | `require` (or stricter) for Supabase |
| `DATABASE_POOLER_MODE` | `auto` | `auto` detects Supabase's transaction pooler by port 6543 |
| `DATABASE_CONNECT_TIMEOUT_SECONDS` | `10` | Fail fast when the database is unreachable |
| `COMPOSE_DATABASE_URL` | bundled `db` | Overrides the DB URL for the compose backend container |
| `CORS_ORIGINS` | `["http://localhost:5173"]` | JSON array of allowed browser origins |
| `MAX_REQUEST_BYTES` | `1000000` | Request body limit |
| `LLM_PROVIDER`, `LLM_MODEL`, `LLM_API_KEY` | unset | Used from Phase 2; the key is never returned by the API |
| `MAX_DEBUG_ITERATIONS` | `3` | Upper bound for the debugging loop (0–10) |
| `VITE_API_BASE_URL` | `/api` | Frontend API base (the dev server and nginx proxy `/api`) |

## Supabase

Supabase is managed PostgreSQL. AgentForge connects to it directly through SQLAlchemy +
psycopg, so authorization stays in the backend; no Supabase client SDK is used.

1. In the dashboard open **Project Settings → Database → Connection string**.
2. Pick a connection type:
   - **Session pooler** (port 5432 on `*.pooler.supabase.com`). Recommended: IPv4, and it
     supports prepared statements and migrations.
   - **Transaction pooler** (port 6543). Works too: AgentForge detects it and disables
     psycopg prepared statements and its own pool, which that pooler does not support.
   - **Direct** (`db.<ref>.supabase.co`). IPv6 only unless the IPv4 add-on is enabled.
3. Put it in `.env`, keeping the driver prefix and URL-encoding the password:
   ```
   DATABASE_URL=postgresql+psycopg://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres
   DATABASE_SSL_MODE=require
   ```
4. `cd backend && .venv/Scripts/alembic upgrade head`
5. Check it: `GET /api/system/status` should report `database.state = "ok"` and
   `database_backend = "postgresql"`.

pgvector is available on Supabase (enable the `vector` extension), so Phase 4 RAG needs no
extra service.

## Migrations

```bash
cd backend
.venv/Scripts/alembic upgrade head                                  # apply
.venv/Scripts/alembic revision --autogenerate -m "describe change"  # after editing ORM models
.venv/Scripts/alembic check                                         # fails if models and migrations drift
```

Review every autogenerated file. `migrations/env.py` uses the same engine factory as the
app, so SSL, timeout and pooler settings also apply to migrations.

## Windows note

On some Windows machines `localhost` resolves to IPv6 `::1` first, and Docker Desktop's
port forward can hang on it. Defaults therefore use `127.0.0.1`, and every PostgreSQL
connection has a connect timeout.

## Retention (planned)

Workspaces and full test logs (Phase 2+) live outside the database under a workspace root.
Rows keep paths, checksums and bounded excerpts. Cleanup of temporary workspaces and old
logs will be a scheduled job with a configurable retention window.

## Troubleshooting

**`password authentication failed for user "agentforge"`**: the password in `DATABASE_URL`
doesn't match the database. The `db` container applies `POSTGRES_PASSWORD` only when its
volume is first created, so changing `.env` later has no effect. Either update the user:

```bash
docker compose exec db psql -U agentforge -d agentforge -c "ALTER USER agentforge WITH PASSWORD '<new password>'"
```

or recreate the volume (this deletes local data): `docker compose down -v && docker compose up -d db`.

**API returns 503 `database_unavailable`**: the backend cannot connect. Check `DATABASE_URL`,
that the database is running, and the backend log line, which gives the driver's reason.

## Google sign-in (Supabase Auth)

Sign-in uses Supabase Auth with Google as the identity provider. The browser gets a
Supabase access token (a JWT). The backend verifies it on every request against the
project's **public** signing keys at `<SUPABASE_URL>/auth/v1/.well-known/jwks.json`
(ES256), so the backend needs no Supabase secret. Every project row has an `owner_id`
and every query filters on the verified user id.

One-time setup:

1. **Google Cloud Console → APIs & Services**
   - *OAuth consent screen*: External; add your email as a test user while in Testing.
   - *Credentials → Create credentials → OAuth client ID → Web application*
     - Authorized JavaScript origins: `http://localhost:5173`
     - Authorized redirect URIs: `https://<project-ref>.supabase.co/auth/v1/callback`
2. **Supabase → Authentication → Sign In / Providers → Google**: enable it and paste the
   Client ID and Client Secret. The secret stays in Supabase, never in this repo.
3. **Supabase → Authentication → URL Configuration**
   - Site URL: `http://localhost:5173`
   - Redirect URLs: add `http://localhost:5173/**`
4. **`.env`**: `SUPABASE_URL`, `VITE_SUPABASE_URL`, and `VITE_SUPABASE_PUBLISHABLE_KEY`
   (Supabase → Project Settings → API Keys → publishable key; the legacy `anon` key also
   works). Restart both the backend and `npm run dev` after changing it.

The publishable key is meant to be public. It only lets the browser talk to Supabase Auth.
Table access through Supabase's Data API is blocked by RLS (migration 0002). **Never** put the
`service_role` / secret key in any `VITE_*` variable.
